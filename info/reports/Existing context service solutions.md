# Nobody has built Zuri's context service yet

No open-source project or commercial product found covers the "Zuri Context Service" as designed, and none even combines its three core ideas: hand-picked Drive files linked M:N to projects, a per-document maintainer who gets AI-found inconsistencies, and a browsable Markdown mirror with diff history. The closest candidates each cover one slice. **Onyx** (open source) and **Dust**, **Guru** and **Glean** (commercial) already offer what the design calls the hardest plumbing: a remote MCP server with per-user OAuth that enforces permissions. **Guru** alone has something like document maintainers, but its version is time-based re-verification of its own cards, not contradiction reports on Drive files. No candidate has a Markdown/git mirror (R3) or a per-project summary that rebuilds itself on change (R4). Those two features, plus the maintainer loop (R2), are the custom part of the design, so adopting any platform would still mean building most of the service, on top of heavier infrastructure or €700+/month in seats. The recommendation is to **build, but on a short list of reused parts**: FastMCP 4.x with its Google OAuth proxy for the connector, Google's official Picker sample, Drive's native Markdown export, the Docs API's suggestion mode for later write tools, and Karpathy's "LLM Wiki" pattern for the summarizer. That brings the MVP plus maintainer loop to about **3.5–5 weeks** of one developer, down from about 4–6. A **second research round on 2026-10-29** examined the 18 vendors the first round had skipped (Graphlit, Langdock, Vectara, Supermemory, Contextual AI, Pinecone Assistant, Ragie, Slite, Tettra, Atlassian Rovo, Box, Egnyte, Notion, Glean, Guru, Onyx EE, Dust, Anthropic's connector directory) plus five more open-source tools. The verdict didn't change: Graphlit is shutting down, Pinecone's Drive connector is end-of-life, and the one product that picks single Drive files and has an OAuth MCP server (Supermemory) lacks maintainers, history, project roles and EU hosting. The pilot still has to confirm that the OAuth connector works end to end in Claude.ai Team.

## Five requirements, zero products that meet more than two

The design ([zuri-context-service.md](zuri-context-service.md)) sets five requirements. R1 is per-file curation of Drive Docs, Sheets and Slides, linked many-to-many to projects. R2 is one maintainer per document, notified about AI-found inconsistencies. R3 is an auto-synced Markdown mirror with diffs and history. R4 is a per-project summary rebuilt on major changes. R5 is a remote MCP server that works as a Claude.ai Team custom connector, with per-user OAuth and per-project roles (admin, member, reader). The candidates scored against them are below (✔ met, ◐ partial, ✘ not met).

On the open-source side, **Onyx** is the strongest candidate. Its official MCP server uses Streamable HTTP, acts as its own OAuth authorization server with dynamic client registration, ships on all editions, and returns only documents the connected user may read ([Onyx MCP docs](https://docs.onyx.app/overview/onyx_anywhere/mcp_server.md)). Its tools are search only (`search_indexed_documents`, `search_web`, `open_urls`), with no full-document read, history or summary tool. The Drive connector's "Specific" mode takes shared-drive URLs, folder URLs or My Drive emails, so per-file picking is not documented ([Onyx Google Drive connector](https://docs.onyx.app/admins/connectors/official/google_drive/overview)). More important for project roles, **"RBAC protection to documents and resources are only available in the Enterprise Edition"** ([Onyx access controls](https://docs.onyx.app/security/architecture/access_controls)). PipesHub and Airweave are weaker: PipesHub's MCP authenticates with a personal access token ([PipesHub GitHub](https://github.com/pipeshub-ai/pipeshub-ai)), and Airweave's Drive connector "does not have any additional configuration options" ([Airweave docs](https://docs.airweave.ai/docs/connectors/google-drive.md)). Dify can publish an app as an MCP server, but "the MCP Server URL contains authentication credentials" with no per-user identity ([Dify docs](https://docs.dify.ai/en/use-dify/publish/publish-mcp)). Open WebUI, AnythingLLM and LibreChat consume MCP rather than serve it. Open WebUI is still relevant for the later "Zuri Hub" phase, not for the context service.

On the commercial side, **Dust** comes closest on access and hosting. Its Drive connector lets admins "granularly select the exact data", syncs Sheets tab by tab, and feeds Spaces ([Dust Google Drive docs](https://docs.dust.tt/docs/google-drive)). Its remote MCP server uses OAuth with dynamic client registration, acts as the signed-in user, and has an EU endpoint at `eu.dust.tt/mcp` ([Dust MCP docs](https://docs.dust.tt/docs/dust-mcp-server)). Pro seats cost **€24/month billed yearly**, and EU residency comes with Business and Enterprise ([Dust pricing](https://dust.tt/home/pricing)). **Guru** is the only product with a real maintainer concept. Every card has a verifier who gets Slack or email reminders when the card is due, and admins can reassign verifiers in bulk ([Guru verification](https://www.getguru.com/features/verification)). Its MCP server's OAuth is "currently approved for: Claude, Cursor" ([Guru help](https://help.getguru.com/docs/connecting-gurus-mcp-server-to-claude-desktop)). **Glean** supports Claude for Teams on the web with OAuth 2.1, PKCE and Google SSO, but bills MCP use in FlexCredits ([Glean MCP docs](https://docs.glean.com/administration/platform/mcp/about)), and buyers report a minimum of about 100 seats ([GoSearch](https://www.gosearch.ai/blog/glean-pricing-explained), a competitor's blog). Claude Team's built-in Drive integration keeps Docs current, but **"is disabled for shared projects"** ([Claude support](https://support.claude.com/en/articles/10166901-using-the-google-docs-integration)), which rules it out as the shared, curated knowledge layer.

## Every vendor sells search; nobody sells the maintainer loop

The pattern behind the scorecard explains why buying doesn't pay. Every product stores Drive content as an opaque index of chunks and vectors and offers permission-aware search on top. That is the commodity part. What Zuri wants, a **curated set of files with a named person responsible for each**, a **human-readable diff history**, and a **summary that rebuilds itself and reports contradictions back to that person**, appears nowhere. The nearest neighbour, Guru, solves a different problem: it asks a verifier on a timer to confirm that a card is still true. It does not detect that the ground-station spec now contradicts the drone spec. Several products also go against the design principle "curated, not crawled". Glean indexes everything a user can access. Google's own Drive MCP server inherits "the same permissions and data governance controls as the user" ([Google Drive MCP guide](https://developers.google.com/workspace/drive/api/guides/configure-mcp-server)) and has no allowlist. Onyx and Airweave select at the folder or drive level.

The economics point the same way. Using Onyx would give Zuri R5 and some Drive plumbing, but R2, R3, R4, per-file selection and project roles would still have to be built. The total comes to roughly the full Zuri MVP **plus 2–3 weeks**, with Vespa/OpenSearch-class infrastructure to run for 30 people and about 500 files, and an EE licence if group-scoped access should come from Onyx rather than custom code. Buying Dust or Guru adds about **€720–750/month** in seats on top of Claude Team, compared with **€10–40/month** of hosting for the in-house design. Much of what those seats pay for (their own chat, agents and model credits) duplicates Claude.ai, which Zuri already pays for. Claude.ai would only use them as an MCP back end. That is the "double-AI" problem: paying twice for the chat layer to get a search layer that the custom service would replace anyway.

The strongest argument for buying is time to value and hosting. If EU-only hosting becomes a hard requirement and nobody can run a server, Dust is the only checked vendor that publicly confirms EU residency at a published price ([Dust pricing](https://dust.tt/home/pricing)). Even then, Dust would cover search and access but not R2–R4. A hybrid (Dust for search, a small custom worker for mirror, summaries and notifications) would carry both the subscription and most of the build.

## Six off-the-shelf parts cut the build by about a week

The parts that can be reused cluster around the riskiest pieces of the design, the OAuth connector and the Drive APIs. The remaining custom code is the registry, the roles and the glue.

| Component | Reuse | What it saves | Caveat |
|---|---|---|---|
| MCP server + OAuth (R5) | **FastMCP 4.x `GoogleProvider` / OAuth Proxy** (Python; 4.1.4 released 26 Oct 2026, 3.x still patched) | ~1 week of OAuth and spec-compliance work | Works on Claude.ai per FastMCP issue #1919's reporter; no published proof for a Team org-wide connector or mobile; open Claude bug #476 (tools not surfaced) |
| Alternative R5 stack | Cloudflare `workers-oauth-provider` + `remote-mcp-google-oauth` template (TypeScript) | Same, on Workers | Back end (Postgres, git) lives elsewhere, which adds a hop |
| Admin UI file picking (R1) | Google's official Picker web sample + `drive.file` scope; Open WebUI's `google-drive-picker.ts` (drive.file, multi-select, since v0.12.3) as a second reference | 1–2 days | Background sync needs a service account or stored user tokens |
| Docs → Markdown (R3) | Native `files.export` with `text/markdown` (10 MB cap) | Converter code | Tables, footnotes and tabs are undocumented; images reportedly come out as base64 data URIs (unverified) |
| Sheets/Slides export (R3) | Sheets API per tab; isaacphi/mcp-gdrive code (MIT) as reference | Small | CSV export covers the first sheet only |
| Summarizer (R4, R2 detection) | Karpathy "LLM Wiki" pattern (gist of 4 April 2026: index, log, schema, lint for contradictions); `lucasastorian/llmwiki` (Apache-2.0) as an MCP-shaped example | Prompt and design work | A pattern, not a library; no implementation syncs Google Drive |
| Later write tools (Phase 2, step 2.4) | Docs API `batchUpdate` with `writeMode: SUGGEST` (real suggested edits) and Drive `comments.create`; Google's hosted Docs/Drive MCP servers or taylorwilsdon/google_workspace_mcp only as reference | Docs API code | Hosted servers are Developer Preview, need restricted `drive.readonly`, no file allowlist |

**FastMCP's `GoogleProvider`** is the key reuse. Google has no dynamic client registration, so FastMCP runs an OAuth proxy that emulates it. The current MCP spec revision (2026-07-28) deprecates dynamic registration in favour of Client ID Metadata Documents (CIMD) ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)); FastMCP has CIMD on by default since 3.0.0 and, since PR #4206 (June 2026), advertises the metadata Claude requires to pick it (`client_id_metadata_document_supported: true` plus `"none"` in `token_endpoint_auth_methods_supported`) ([FastMCP PR #4206](https://github.com/jlowin/fastmcp/pull/4206)). It exposes the caller's email in tools through `get_access_token().claims.get("email")` or `CurrentAccessToken()` ([FastMCP Google integration](https://gofastmcp.com/integrations/google); [FastMCP OAuth Proxy](https://gofastmcp.com/servers/auth/oauth-proxy)). That email is exactly what the per-project role check needs. It also covers most of Claude's strict connector rules: mandatory S256 PKCE, a `401` with `WWW-Authenticate: Bearer resource_metadata=...`, a PRM `resource` equal to the URL the user typed, form-encoded `/token`, 10-second discovery and token timeouts (30 seconds for refresh), rotating refresh tokens, and the redirect URI `https://claude.ai/api/mcp/auth_callback` ([Claude connector authentication](https://claude.com/docs/connectors/building/authentication)). Claude's own docs rule out the shortcut: static-header auth sends the same key for every member and should not be used "to identify which user is calling", so per-user roles require OAuth ([Claude connector authentication](https://claude.com/docs/connectors/building/authentication)). The official MCP Python SDK (now v2) gives "the resource-server half: verify, advertise, refuse" and no login flow ([MCP Python SDK](https://py.sdk.modelcontextprotocol.io/run/authorization/)), and the TypeScript SDK froze its proxy provider in a legacy package, so a separate authorization server would still be needed. FastMCP or Cloudflare's `workers-oauth-provider` (MIT, targets MCP 2026-07-28, its Google demo has a `HOSTED_DOMAIN` setting) ([GitHub](https://github.com/cloudflare/workers-oauth-provider)) provides one; hosted alternatives with CIMD support are WorkOS AuthKit (free to 1M monthly users), Stytch, Auth0, Descope, Scalekit and Clerk. FastMCP stores `email` and `email_verified` but no `hd` claim, and Google says the `hd` parameter is only a UI hint, so the Zuri domain must be enforced server-side on the email claim, with an "Internal" consent screen as a second barrier. Production also needs an explicit `jwt_signing_key`, an encrypted Redis client store, and `302`/`303` redirects (a `307` was the real cause of one of the Claude.ai OAuth failures below).

On the Drive side, Google lists **Markdown export for Google Docs only**, capped at 10 MB per export ([files.export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)). Sheets CSV/TSV export is "first-sheet only" ([Google export MIME types](https://developers.google.com/workspace/drive/api/guides/ref-export-formats)), which confirms the design's plan to read each tab through the Sheets API (`spreadsheets.values.batchGet`, 60 reads per minute per user). Google has not documented how the Markdown export handles tables, images, footnotes or tabbed documents. Third-party reports say images are embedded as base64 data URIs and headings get Pandoc-style `{#id}` anchors ([wayofmarkdown](https://wayofmarkdown.com/markdown-in-google-docs), [gdrivemd tutorial](https://www.zonca.dev/posts/2026-05-24-gdrivemd-tutorial), both unverified), and per-tab export is officially unsupported ([Google Workspace Developers](https://dev.to/googleworkspace/exporting-individual-tabs-from-google-docs-as-pdfs-2903), [issue 379170478](https://issuetracker.google.com/379170478)), so whether the Markdown export includes all tabs is a pilot test item. Docx plus pandoc is a fallback for difficult files. Google's native `.md` support in Drive and Docs (5 Oct 2026) is for editing `.md` files stored in Drive, not for exporting Docs ([Workspace Updates](https://workspaceupdates.googleblog.com/2026/10/preview-edit-and-collaborate-on-Markdown-files-natively-across-Drive-and-Docs.html)). The only tool that resembles the sync worker, **wikiGDrive**, converts a whole Shared Drive to Markdown ([wikiGDrive](https://github.com/mieweb/wikiGDrive), MIT, last push August 2026); gdrivemd, gcmd, gdocs-git-sync and md-gdoc are small per-document CLIs. None does Picker-based per-file selection with a git mirror, and the worker itself is about 200–400 lines of glue. For the summarizer, **Karpathy's LLM Wiki gist** (4 April 2026) maps almost one-to-one onto the mirror layout: immutable sources map to `docs/`, the LLM-maintained wiki and `index.md` to `SUMMARY.md` and `INDEX.md`, the append-only log to `CHANGES.md`, and a schema file to a repo `CLAUDE.md`. Its "lint" operation explicitly looks for contradictions, which "still benefit from human review" ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). That human review is the maintainer loop. Of its open-source implementations, `lucasastorian/llmwiki` (Apache-2.0) is the closest in shape, with an MCP server offering `search/read/lint` tools to Claude.ai, but none of them syncs Google Drive ([llmwiki](https://github.com/lucasastorian/llmwiki)).

Revised against the design's phase plan, the effort looks like this. Phase 0 (pilot) stays at **about 1 week**. Phase 1 (registry, Picker admin UI, OAuth MCP with read tools) drops from 2–3 weeks to about **1.5–2 weeks**, because FastMCP removes most of the OAuth work and the Picker sample removes UI guesswork. Phase 2 (issues, notifier, proposals, incremental and full summaries) stays at **1–2 weeks**, since no reusable maintainer workflow exists. That gives **3.5–5 weeks** in total, compared with 4–6. The saving is modest because the parts that can't be bought are also the ones that can't be reused.

## The pilot has to retire four specific risks

The biggest remaining uncertainty is not whether to build but whether Claude.ai behaves as the design assumes. The two OAuth failures the first round cited are now closed and were server-side: #313 was a method-preserving `307` redirect that made the browser POST to Claude's GET-only callback, and #212/#122 were callbacks arriving without a `code` parameter ([claude-ai-mcp #313](https://github.com/anthropics/claude-ai-mcp/issues/313); [#122](https://github.com/anthropics/claude-ai-mcp/issues/122)). FastMCP's own "Google OAuth doesn't work for Claude.ai" issue was fixed in late 2025 and its reporter confirmed `GoogleProvider` works on Claude.ai and Claude Code ([FastMCP #1919](https://github.com/jlowin/fastmcp/issues/1919)). What remains: no published proof for a Team org-wide connector or for mobile, and an **open Claude-side bug** since June 2026 in which connectors show "Connected" on claude.ai web but their tools are sometimes never offered to the model, affecting FastMCP and non-FastMCP servers alike, with no Anthropic reply ([claude-ai-mcp #476](https://github.com/anthropics/claude-ai-mcp/issues/476)). Claude Tag's identity question is now answered by the docs: a connector attached to a channel "belongs to the agent identity, not to any person", so channel calls arrive as one admin account; per-user identity exists only through personal connectors (on by default for Team orgs) and in DMs ([agent identity](https://claude.com/docs/claude-tag/concepts/agent-identity); [personal connectors](https://claude.com/docs/claude-tag/concepts/personal-connectors)).

| Verify in the pilot | Why it matters | Fallback if it fails |
|---|---|---|
| FastMCP 4.x `GoogleProvider` completes OAuth as an Owner-added Team connector, on web and mobile, Claude picks CIMD, the email claim reaches tools, and the tools appear in chats (#476) | All per-project roles depend on it | Cloudflare `workers-oauth-provider`, or a hosted auth vendor (WorkOS, Stytch, Descope); Claude Desktop/Code while #476 lasts |
| The connector works inside *shared* Claude.ai projects for all members (undocumented) | The UX is one shared project per Zuri project | The GitHub-mirror route with manual "Sync now" |
| Claude Tag: a service user per channel bundle versus relying on personal connectors; which the members accept | Group chat roles | Scope each Slack channel to one project |
| `text/markdown` export quality on 3–5 real Zuri docs (tables, base64 images, footnotes, tabs, comments), plus Sheets per-tab rendering | Mirror and summary quality | docx + pandoc for difficult files; Docs API per tab |
| `drive.file` + Picker versus a service account for background sync (does a service account get a 404 on a picked file it wasn't shared?) | Sync reliability when files sit in many people's My Drives | Share picked files with a service account or a Shared Drive |
| Token cost of incremental versus full summary rebuilds; the Team plan's pooled API credits (up to $500/month) cover the summarizer's API key | Summarizer billing | API key with a monthly spend cap |

A cheap parallel check would also pay off. A two-week **Dust trial** would settle whether its Drive picker allows single files and one file in several Spaces, and whether its MCP server works in Claude.ai. Dust's MCP server exists with OAuth (DCR and CIMD) at `dust.tt/mcp` and `eu.dust.tt/mcp`, but its docs name no client ([Dust MCP docs](https://docs.dust.tt/docs/dust-mcp-server)), and the Drive docs don't confirm single-file picking ([Dust Google Drive docs](https://docs.dust.tt/docs/google-drive-connection)). If both work and EU hosting is mandatory, Dust becomes a credible R1/R5 back end behind a slimmer custom service.

## Round 2 (2026-10-29): eighteen more vendors, same verdict

The first round left about a dozen vendors unexamined. A second round checked them against R1–R5, pricing, EU residency and Claude.ai compatibility. Headlines: **Graphlit is winding down** (new signups closed, free-tier export deadline 1 Aug 2026, embeddings and connector credentials not exportable; [Graphlit sunset](https://www.graphlit.com/legal/sunset)). **Pinecone's Marketplace Drive connector**, the only Pinecone path with a file picker, reached end of life on 31 Aug 2026 ([Pinecone release notes](https://docs.pinecone.io/release-notes/2026)). Two of the closest-fit "context layer" vendors therefore disappeared inside the research window, which is itself an argument for a self-owned, exportable git mirror. Only **Supermemory** picks individual Drive files through a hosted Picker *and* exposes an OAuth MCP server; it converts Docs to Markdown internally ("lossy"), keeps no visible history, has no owners, project roles or EU region, and its unlimited-seat plan costs $399/month ([Supermemory Drive connector](https://supermemory.ai/docs/memory-api/connectors/google-drive); [Supermemory MCP](https://supermemory.ai/docs/supermemory-mcp/introduction); [pricing](https://supermemory.ai/pricing)). **Guru** remains the nearest thing to R2: exactly one verifier per card, daily Knowledge Agent reviews that can auto-unverify content and send a digest to owners, and weekly duplicate detection, but for staleness rather than contradictions, and its Drive sources are folders or whole drives ([Guru verification](https://help.getguru.com/docs/verifying-and-unverifying-cards)). Nobody sells a human-readable Markdown/git mirror (R3) or a self-rebuilding project summary (R4).

## What this research still does not cover

Remaining gaps after two rounds: **Bloomfire** and **Fini** (both market AI contradiction or conflict detection routed to a reviewer, neither mentions Google Drive; vendor claims only), **Coda**, and the exact per-file and multi-Space behaviour of Dust's Drive selection. Hosted MCP auth vendors were compared on CIMD support and entry pricing but not tested against Claude.ai. Whether Google's hosted Workspace MCP servers will leave Developer Preview is unknown. By category, the developer RAG APIs (Vectara, Pinecone, Contextual AI, Ragie) could at most replace the sync and search layer, not the registry, maintainer workflow or roles. Tools like Confluence/Rovo, Box, Egnyte, Slite and Tettra require moving content into their own store, which breaks the rule "Drive stays the master".

## Conclusion

The market has made per-user, permission-aware MCP search a commodity, and that changes the question. Zuri's design is no longer risky at the connector layer, which is now about 20 lines of FastMCP configuration (plus a Redis store, a signing key and an email-domain check for production). The value is in the part nobody sells: **accountability for documents**. Who owns this spec, what changed in it last week, and who should hear that it now contradicts another one. That is a workflow problem, not a retrieval problem, which explains why search vendors haven't built it and why it fits the small custom service the design describes.

The practical consequence is to treat search as replaceable inside the build. Start with Postgres or SQLite full-text search behind the Zuri MCP tools. If semantic search over large projects becomes necessary in Phase 3, plug in Onyx, Dust or a RAG API *behind* the Zuri server, scoped by project, rather than in front of it. The registry, mirror, summaries and maintainer loop then stay Zuri's own, and every search back end becomes a swappable part rather than a platform to migrate off.

## Addendum: implications of master-plan.md (2026-10-29)

[master-plan.md](master-plan.md) adds a Phase 3 in which the service is sold to other companies at about $5/user/month. That changes how some findings read:

- **The candidates become competitors.** Dust (~€24–30/seat), Guru (~$25/seat, third-party figure) and Glean (enterprise pricing) sell search plus their own chat. A $5 product competes on curation, document ownership (the maintainer loop) and "plugs into the Claude you already pay for", not on search. The gap this research found (nobody does R2–R4) is the product's differentiation.
- **Licences matter for reused parts.** Open WebUI's licence forbids changing its branding for deployments over 50 users without an enterprise licence ([Open WebUI licence](https://docs.openwebui.com/license/)), so it's only suitable as a throwaway prototype, not as the base of the Phase 2 Hub that Phase 3 resells. The reused building blocks recommended above have permissive licences (FastMCP, Google samples, Cloudflare `workers-oauth-provider`, `taylorwilsdon/google_workspace_mcp`: MIT/Apache), as do Onyx's MIT core parts if used as reference code.
- **`drive.file` is also the right scope for a public product.** It's a non-sensitive scope that needs only basic Google app verification. Restricted Drive scopes would require a yearly CASA security assessment ([Google Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)).
- **Distribution via Claude's connector directory** requires a remote server over HTTPS, OAuth 2.0, a `title` plus `readOnlyHint`/`destructiveHint` on every tool, separate read and write tools, and a privacy policy, documentation URL, support contact, icon and test account ([Claude connector submission](https://claude.com/docs/connectors/building/submission); [review criteria](https://claude.com/docs/connectors/building/review-criteria)). Any Owner on a paid plan can submit; listings start as "Community" after an automated scan ([publish to the directory](https://claude.com/docs/directory/publish)). The FastMCP-based design can meet all of these.
- **The Team plan's pooled API credits** ($20 per Standard seat per month, capped at $500 per org) cover the Messages API, Managed Agents and the Agent SDK ([API credits for subscribers](https://platform.claude.com/docs/en/about-claude/api-credits-for-subscribers)). For Zuri they pay for the summarizer; for Phase 3 customers they mean a "bring your own Claude" product can also offer API-billed summaries that most Team customers will never see on a bill.
- **Claude Tag channel connectors run under a shared agent identity**, with per-user identity only via personal connectors or DMs ([agent identity](https://claude.com/docs/claude-tag/concepts/agent-identity)). The design's Phase 1 Slack setup was adjusted accordingly (service user per channel, or personal connectors).
- **Identity stays bought, not built.** master-plan.md notes that everyone at Zuri has a Google account and a Zoho Mail account, both with OAuth. Zoho Accounts is an OpenID Connect provider whose ID token carries `email` and `email_verified` ([Zoho OIDC](https://www.zoho.com/accounts/protocol/oauth/sign-in-using-zoho.html)), and FastMCP's generic `OIDCProxy` can front such a provider ([FastMCP OIDC proxy](https://gofastmcp.com/servers/auth/oidc-proxy)). But one FastMCP server runs a single interactive login provider: `MultiAuth` only adds token verifiers ([FastMCP MultiAuth](https://gofastmcp.com/servers/auth/multi-auth)). So the Phase 1 connector stays Google-only (the Picker needs Google anyway) and Zoho becomes a second login for the Phase 2 Hub. Nothing in this report's build-vs-buy verdict changes.
- **The Phase 2 UI is now specified** in the user-written design.md (a Slack-like three-pane layout with an icon rail, a conversation list with a per-project Files view, and a wide main pane). It confirms the own-build decision above; Zulip's data model and Open WebUI's Picker code remain reference material only.
